# Testing and fake data

One of the [reasons we built eltstar](../README.md) is that testing elt/etl pipelines is usually an afterthought. We wanted schema-valid, halfway-realistic test data to be a byproduct of defining your tables, not a separate effort.

You've already seen part of this: every [`Column`](../core_concepts/model_driven.md#table-instances) can carry a `generation` attribute.

```python
channel_id=Column(
    name="channel_id",
    data_type=StringType(),
    is_primary_key=True,
    generation=Generation(faker_type=FakerStringType()), # (1)!
),
```

1. `Generation` is a thin wrapper around a `FakerType` - it exists as its own model so we have a place to grow generation options that aren't tied to `faker` later on, without breaking the `Column` interface.

This page covers what actually happens when you ask eltstar to generate data for a table, and the `FakerType`s available to you out of the box.

## Generating data for a table

```python
from eltstar.testing.faker_manager import FakerManager
from eltstar_engine_polars.engine import PolarsEngine

fake_channels = FakerManager().generate(table=tech_channels, engine=PolarsEngine(), n_values=20) # (1)!
```

1. This returns a `DataFrameWrapper` with `n_values` rows, one fake value per row for every column that has a `generation` set. Columns without a `generation` are simply left out of the result - eltstar can't invent a strategy for you.

The result is engine aware (backed by `engine.dataframe_from_faker_columnar`), so you can write it straight to a table the same way you'd write any other `DataFrameWrapper`:

```python
tech_channels.write(runtime_config=..., environment_config=..., data_frame_wrapper=fake_channels)
```

This is exactly the pattern used to seed local/test data before running transformations against it - see the [minimal example](https://github.com/jochengietzen/eltstar/tree/main/examples/eltstar_minimal_example) for a fully worked-through pipeline that does this end to end.

## Built-in `FakerType`s

All of these live in `eltstar.testing.faker_type` and wrap a corresponding [`faker`](https://faker.readthedocs.io/) call:

| Class | Produces |
| --- | --- |
| `FakerStringType` | a single word |
| `FakerTextType` | a sentence/paragraph of text |
| `FakerIntType(min_val, max_val)` | an integer in `[min_val, max_val]` |
| `FakerIDType` | a `uuid4` string |
| `FakerTimestampTypeSecondsUTC` | a UTC-aware `datetime` |

If none of these fit, subclass `FakerType` and implement `__call__(self, *, faker_: Faker, **kwds) -> Any` - anything the `faker` library can produce is fair game.

## Simulating referential integrity

Fake data usually needs more than "give me a random value per row" - foreign-key-like columns need to actually repeat across tables, or a primary key column needs its values to reuse themselves in the *same* column across rows without becoming pure duplicates. Every `FakerType` accepts three extra arguments for this:

```python
FakerIDType(
    generation_id="channel_id", # (1)!
    reuse_percentage_min=0.3, # (2)!
    reuse_percentage_max=0.8, # (3)!
    allow_duplicate_values=False, # (4)!
)
```

1. Two `FakerType` instances (in the same table, or across different tables generated by the same `FakerManager`) that share a `generation_id` draw from the *same* pool of generated values. This is how you keep e.g. a `channel_id` foreign key column consistent with the primary key column it references - give both `Column`'s `FakerType` the same `generation_id`.
2. / 3. For each generation call, a random reuse percentage between these two bounds decides how much of the column is filled from the shared pool versus freshly generated values. This keeps the fake data from being either "every row is a duplicate" or "nothing ever repeats".
4. If `False` (the default), values are drawn from the pool via `random.sample` (no duplicates within this generation call, using `faker.unique`). If `True`, values are drawn via `random.choices` (duplicates allowed), which makes sense for a foreign key column that legitimately repeats.

Without a `generation_id`, every value is generated completely independently - fine for things like `description` or `country`, not fine for anything you intend to join on later.

## Using this in `pytest`

`eltstar.testing.utils.parametrize_for_tests` turns every currently registered transformation into a `pytest` parameter, complete with a `GenerateFixture` per input table:

```python
import pytest
from eltstar.testing.utils import parametrize_for_tests
from eltstar.transformation import manager

@pytest.mark.parametrize(
    "case",
    list(parametrize_for_tests(manager)), # (1)!
    ids=lambda case: case.name,
)
def test_transformation_smoke(case, faker_manager, engine):
    inputs = {
        name: fixture(faker_manager=faker_manager, engine=engine) # (2)!
        for name, fixture in case.input_models.items()
    }
    result = case.transformation.func(**inputs)
    # assert whatever schema/shape guarantees matter to you
```

1. Each `case` is a `ParameterizedTest(name, transformation, input_models)` - one per registered transformation.
2. Calling a `GenerateFixture` (via `fixture(faker_manager=..., engine=..., n_values=100)`) generates schema-valid fake data for that specific input table, using the same `FakerManager.generate` shown above.

This gives you a smoke test for every transformation in your pipeline - "does this function run at all against schema-valid input" - without hand-writing fixtures per transformation. It won't catch business-logic bugs, but it reliably catches the kind of breakage a refactor introduces (renamed columns, changed types, a transformation that was never updated after its input table changed).
